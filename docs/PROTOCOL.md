# GSK UDP file service: восстановленный формат

Это описание наблюдаемого протокола, не спецификация производителя. Основание: дизассемблирование установленной `MiniSock.dll` из GSKComm-M 2.6 build 2274 и реальные обмены с контроллером в локальной сети от 2026-11-07. Модель и версия прошивки контроллера отдельно не определялись.

DLL: PE32 x86, 73 728 байт, image base `0x10000000`, SHA-256 `2D97F6A8964AA9AFA9C867D4D158278238E696F404E7AC5D6DE21525A4214779`. Виртуальные адреса ниже относятся именно к этому файлу. Программе DLL не требуется.

## Транспорт

UDP, адрес контроллера задаётся пользователем, порт по умолчанию 6000. Один запрос за раз; ответ с того же адреса и порта. Клиент использует connected UDP socket. Числа длиной более байта — little-endian.

Пять байт внешнего заголовка запроса:

| Смещение | Значение |
|---|---|
| 0 | CRC-8 по байтам 1–4: polynomial `0x07`, init 0, MSB-first, xorout 0 |
| 1 | Логический адрес клиента |
| 2 | Сервис клиента: `12` |
| 3 | Логический адрес сервера: `100` |
| 4 | Сервис сервера: `12` |

Логический адрес клиента взят из последнего октета IP выбранного интерфейса, с заменой 0/100/254/255 на 25. Это способ выбора из исследованной реализации, не физический MAC-адрес. В ответе адреса и сервисы переставлены. **В реальном ответе байт 0 равен `01`, он не совпадает с CRC заголовка запроса.** Native-парсер `0x10002e80` копирует этот байт без проверки; Rust делает так же. Проверяются адреса, сервисы, sequence и операция. UDP-контрольная сумма не является криптографической аутентификацией; сам протокол аутентификации в исследованном обмене не содержит.

Формирование заголовка: `0x10003350`; CRC: `0x10002db0`; обработка принятого заголовка: `0x10002e80`, маршрутизация: `0x10002f30`.

После пяти байт начинается payload. Все последующие смещения в документе считаются **от начала payload**:

| Смещение | Тип | Значение |
|---|---|---|
| 0 | u16 | sequence: ответ повторяет номер запроса |
| 2 | u8 | семейство: 0 |
| 3 | u8 | операция: младшие 6 бит; `0x80` — ответ; `0x40` — ошибка |
| 4 | bytes | тело операции |

Клиент увеличивает sequence с переполнением u16; при повторе запроса сохраняет тот же номер и содержимое. Начальное значение различается между запусками. Принимает только ожидаемую операцию/номер, игнорирует короткие, чужие и запоздавшие датаграммы. Ограничение ответного пакета клиента — 4096 байт; блок полезных файловых данных — 1024 байта.

Удалённая строка пути: u16 числа ASCII-байт **включая NUL**, затем строка и `00`. По умолчанию `/user/NCPROG/O1234.CNC`. Ограничения ASCII/255 байт и формата Oxxxx.CNC установлены клиентом; иные кодировки не исследованы.

## Файловые команды

| Op | Назначение | Тело запроса, с offset 4 | Успешный ответ |
|---|---|---|---|
| `3F` | Mount файловой сессии | u16 subcmd=3; строка длины 1: `00` | u16 subcmd на 4, далее данные; ошибка u16 на 6 |
| `06` | Stat | строка пути + два нулевых padding-байта | u16 data length на 4; структура на 6; ошибка u16 на 4 |
| `01` | Open | u16 mode; строка пути | mode на 4; reserved на 6; u16 handle на 8; ошибка на 8 |
| `03` | Write | u16 handle; u16 count; u32 offset; данные | handle на 4; count на 6; offset на 8; ошибка на 12 |
| `02` | Read | u16 handle; u16 count; u32 offset | handle на 4; count на 6; offset на 8; данные на 12; ошибка на 12 |
| `04` | Close | u16 handle | u16 handle на 4; при error flag код может отсутствовать |

Open: `0x001A` — создать/перезаписать с усечением, `0x0011` — читать. Именно семантика усечения проверена записью 80 байт, затем 40 байт: прочитано ровно 40. В stat наблюдалась структура из 52 байт: `mode` u32 на смещении 8 структуры, `size` u32 на 28. Остальные поля не интерпретируются.

Read: конец файла возвращается ошибкой `0x8011`. **При EOF поля count и offset могут содержать устаревшие данные**: в реальном пакете для offset `0x3D28` пришёл `0x003D3D28`. Их нельзя проверять как обычные данные. Клиент принимает EOF только если общее число ранее считанных байт совпало со stat. Нулевой успешный блок без EOF считается некорректным.

Write: подтверждение должно повторить handle, offset и полный count. Короткое подтверждение или неверное смещение — ошибка. Close проверяется отдельно; ошибка закрытия не становится успехом передачи. При ошибке без отдельного кода используется native fallback `0x800A`.

Наблюдавшиеся ошибки: `0x8011` — EOF; `0x8012` — файловая сессия не смонтирована; `0x8016` — файл/путь не найден. Другие коды выводятся как есть, без придумывания смысла. Только `0x8016` в предварительном stat разрешает создание отсутствующего файла.

Native-адреса: open `0x10003ec0`, stat `0x100040b0`, read `0x10004290`, write `0x10004500`, close `0x10004770`, mount/general `0x100055a0`. Обработка EOF при приёме файла: `0x10006795`.

## Каталог

| Op | Назначение | Запрос | Ответ |
|---|---|---|---|
| `08` | OpenDir | u16 mode=`0x0100`; строка пути | mode на 4, handle на 6; ошибка на 6 |
| `0A` | ReadDir | u16 handle; u16 requested bytes=1024 | handle на 4, u16 entry count на 6, u16 data size на 8, данные на 10; ошибка на 8 |
| `09` | CloseDir | u16 handle | handle на 4; ошибка на 6 |

ReadDir двигает внутренний указатель. На станке страницы содержали до 15 записей, даже при запросе 1024 байт. Терминальная страница: count=0, data size=0; подтверждено полной выгрузкой каталога.

Запись каталога: u32 длина всей записи на 0; u32 mode на 4; u32 размер файла на 8; три u32 поля времени на 12/16/20 (не декодируются); NUL-имя на 24; padding до кратности 4. Пример программы: 36 байт, mode `0x00100600`. Проверяются длина записи, наличие NUL и согласованность count/data size. Mode-маска `0x170000`, признак каталога `0x040000`; обычные файлы подтверждены железом, каталоги внутри каталога программ не проверялись. Не-UTF-8 имена выводятся с заменой нераспознанных символов, управляющие символы экранируются.

Native: OpenDir `0x10004ae0`, ReadDir `0x10004e60`, CloseDir `0x10004cc0`, итератор записи `0x10006c30`.

## Повторы и ограничения

Повторяются только mount, stat и read/write с явно заданным смещением. Повтор записи отправляет тот же блок в то же смещение. Потери ответов проверены локальным UDP-эмулятором; искусственно нарушать связь с работающим станком не стали.

Open/close и ReadDir не повторяются: неизвестно, насколько сервер умеет устранять дубликаты, а повторный запрос может менять состояние. При их таймауте CLI сообщает неопределённость результата. Нет атомарного remote rename/commit; прерванная передача может оставить часть файла.

Исследован именно Ethernet file service. Другие экспорты MiniSock, discovery, параметры станка, RS-232, DNC и удалённое выполнение не реализованы. Текст CNC не анализируется и не переписывается. Проверка SHA-256 подтверждает равенство содержимого, а не технологическую корректность программы.

Сырые read-only пары запрос/ответ: `research/wire-fixtures.json`. Протокол воспроизведён самостоятельным Rust-кодом без FFI и без встраивания исходного DLL.
